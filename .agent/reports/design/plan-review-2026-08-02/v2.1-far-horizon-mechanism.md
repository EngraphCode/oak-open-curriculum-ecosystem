### W2 — Identity and theme contract

The strategic kernel made mechanical. Direction settled: identity is an
**authored configuration surface** — a JSON-Schema **identity manifest** (assets,
voice, polarity default, composition preferences, theme roster, OS-signal
bindings) plus per-theme token trees, plus a declared, bounded, VALUE-FREE
**identity CSS layer** (permitted selector shapes only; `var(--role)` references
only — EX37); an **identity emitter** generates brand CSS + asset manifest +
theme roster from it. **The Oak asymmetry, stated (EX0/EX57)**: Oak authors no
manifest token block — a **CSS→DTCG projection generator** (W2.2, discharging
ADR-213 §2's existing regenerated-export obligation) derives Oak's token
projection from the kit CSS, and Oak's manifest REFERENCES that generated
projection while carrying the non-token axes (assets, voice, polarity, roster,
bindings); non-Oak identities author their token blocks. No Oak token is ever
authored twice; the dated ADR-213 §2 amendment records exactly this split.
Input: W0.4's identity census (L2; W0 precedes W2 by the sequencing chain).
Owning workspaces: `design-tokens-core` for schema + validators + emitter
mechanism; the W2.0 home for identity DATA; the kit's public surface unchanged.
Describing surface: schema/emitter unit fixtures + the W2.5 gate matrix cells.

### W3 — The React component tier

On the ADR-213 §3 shape — CURATED adoption. Coverage means a recorded mapping
DECISION for every W0.1 component class, where the DEFAULT decision is
**no-construct / stays-class-only** (Director ruling on EX18/EX68); a component
is minted only at a named materialised need under the curation criterion:
interaction model, prop variance, repeated composition across pages. The
coverage reading of the owner's "full optional React component set" is carded to
him at W3.0 open (frontmatter gate 4, FR9). Describing surface: tier unit tests
(prop→class mapping + fixtures parity) + the W2.10 rendered gate.

- **W3.0 Packaging, landing-sequence obligations + the mapping rule.** FIRST,
  the packaging story (EX14 — without it every `'use client'` directive is
  silently discarded at build): per-component subpath `exports` (or
  preserve-modules), a directive-preserving build step, `external`
  react/react-dom/jsx-runtime, `react`(+`react-dom`) as `peerDependencies`
  with devDependency mirrors on the `oak-design-ink` precedent, `jsx:
  react-jsx`. The mapping rule recorded in the coverage table's contract:
  recipe class → component **only at curated need**; modifier class →
  prop/variant union; layout primitive → composition component; utility →
  `className` passthrough; **no-construct / stays-class-only is the default
  outcome** — demonstrated in the showcase via `className`. Completeness is
  MECHANICAL (L3/D16): a check consuming the W0.1 census fails when any class
  lacks a recorded decision (one row per class, zero unmapped, red-proven on a
  planted census class). The dated **ADR-213 §3 amendment** lands as an
  acceptance line (EX56, Director-confirmed with the both-shapes precision):
  it records BOTH consumption shapes' roles — the studio seeds remain the
  tier-3 token-sufficiency proof (peer consumption, fixtures-guarded,
  unchanged in purpose), and ADOPTED tier components paint via kit recipe
  classes (one recipe definition — the structurally stronger form of the
  no-fork invariant the re-wrap rejection protects); the REJECTION and the
  curation doctrine are explicitly unchanged. Fixtures-as-parity is RESTATED
  at its re-homing (EX25): under kit-class painting it is a class-selection
  contract per prop combination, no longer an independent-implementation
  drift check. The §3 landing-sequence set rides the first component export:
  ADR-041 map note, `.design-sync/conventions.md` rewrite + re-sync, the
  fixtures-parity migration (re-homed from `ws-fixtures-parity`, dated
  amendment — §Relationships). Acceptance (`repo-safe`: the packaging tests;
  the amendments in the landing PR diff; the completeness check red-proven).
- **W3.1 Curated adoption, sliced by component family.** A FAMILY is one
  recipe-class census row plus its modifier/element classes (L1) — grouping
  mechanical from the census + mapping table, the count following the census.
  Each family a single-story PR: adopted components REWRITTEN at adoption —
  consume kit classes with variants as props; `useState` state-mirroring
  deleted in favour of CSS state semantics; no `style` prop. The
  **construction-path decision is stated per interactive family** (EX19): Base
  UI headless primitives are the §3 default (pinned exact, adopted at
  materialised need), hand-roll only with a recorded ground; the §3 app-shell
  prerequisites (`isolation: isolate` on the app root; `position: relative`
  on `body`) land in the REACT app shells — showcase and styled demo — as
  part of their portal-bearing landings (the plain demo takes none). The tier
  prop-API contract: `className` accepted and merged after kit classes
  (presence, not victory — the sanctioned VARIATION route is a kit modifier
  class or a declared set of custom-property hooks the component sets on its
  root, EX26); ref as a prop; polymorphism via a render/`asChild` slot with
  the rendered element union constrained to `button | a` (EX24 — no
  `next/link` in the tier); fixtures-as-parity per W3.0's restatement. Unit
  tests carry prop→class mapping + parity; keyboard/focus/dismissal criteria

  tests + the parity file; RED: the family's first fixture. Acceptance
  (`repo-safe`: W2.10's gate green per family; coverage table rows).
- **W3.2 Theme runtime completion.** The kit contract restated structurally
  (EX13): **listeners fire from `apply()`** — the single application point —

- **W3.3 Identity runtime binding.** Identity becomes a KIT-OWNED runtime
